For a repository-status or plan review, establish the current branch, ahead/behind state, worktree changes, and recent commits before assessing feature progress. Separate committed work from uncommitted IDE artifacts and untracked files.\n2. Read the portal plan's current-state table, sprint breakdown, tests, and Definition of Done. Treat plan checkboxes and prose as requirements, not proof of implementation; compare every claimed completion against current source files, routes, TODOs, and test projects.\n3. Run `dotnet test Klinara.slnx --no-restore` and report the actual totals and warnings. A passing unit suite does not establish integration or end-to-end completion. Check specifically for controller integration tests and Playwright coverage when the plan requires them.\n4. For frontend review, inventory all portal pages and reusable components, then follow the actual user flow: email entry → OTP send/validation → doctor/slot retrieval → booking → confirmation/view/cancellation. Verify API calls, dynamic clinic/subdomain context, validation, errors, and loading states; don't describe placeholder UI as integrated functionality.\n5. Compare the observed state to acceptance criteria and report only the remaining work, grouped by sprint or priority. Flag plan sections that are stale and distinguish an existing configuration file from versioned/deployment configuration.\n\n## Implementation and review rules\n\n- Keep OTP purpose consistent between OTP creation and validation; test both sides of the flow.\n- When validating OTP with `_userManager.VerifyUserTokenAsync`, pass the 6-digit code directly without padding — Identity expects the exact token, not a padded 32-char string. Padding the code causes validation to fail because the reconstructed token doesn't match the stored format.\n- Enforce clinic and patient scoping, token expiry/single-use, booking horizon, and strike blocking in server-side services, not only in the UI.\n- Treat Razor `RZ10012` unknown-component warnings as functional defects: a successful build can still render an unresolved custom element when its component namespace is missing or wrong.\n- Report nullable/compiler warnings explicitly when the Definition of Done requires a warning-free build; passing tests do not erase build warnings.\n- Refresh plan status when implementation changes so obsolete “missing” lists don't mislead the next review.\n- **OTP generation must use only `EmailVerification` purpose** — do not generate a `Login` OTP first and then an `EmailVerification` OTP; a single `EmailVerification` code is emitted per portal verification request. The test `SendVerificationEmailAsync_GeneratesOnlyEmailVerificationOtp` validates this guardrail.\n- Do **not** add a unique index on `{ClinicId, Type, PatientId}`: token history persists after use, and patients must be able to receive multiple tokens of each type over time. The existing unique index on the random token value is appropriate; enforce active-token policy explicitly only if product requirements demand it.\n- **User preference: deliverables should be concise and direct, matching the weight of the ask without filler or restatements.** No «Great question,» no restating the request, no re-summarizing what already was said. Plain claims over adjectives; when unsure, say so plainly. This preference applies across sessions regardless of task.\n- **Render mode**: Declare `@rendermode InteractiveServer` on pages that use interactive components (`@onclick`, `@bind`, etc.). Pages that only use static navigation can omit it. Declaring it globally in `Routes.razor` or `App.razor` can open too many circuits and degrade performance.\n- **DoctorSelector/SlotPicker integration**: These components need `IScheduleService` injected via DI. `DoctorSelector` should call `_slotService.GenerateSlotsForPeriodAsync(clinicId, doctorId, startDate, endDate)` to populate slots for the UI. `SlotPicker.ConfirmSelection()` should navigate to a confirmation page using `NavigationManager.NavigateTo()` with the slot and doctor IDs.\n\n## Recent learnings (2026-11-24)\n\n- **OTP single-purpose emission**: `PatientPortalService.SendVerificationEmailAsync` previously generated a `Login` OTP and then an `EmailVerification` OTP; this was changed to emit a single `EmailVerification` code only. The test `SendVerificationEmailAsync_GeneratesOnlyEmailVerificationOtp` validates this guardrail.\n- **SendLoginOtpAsync removal**: `PatientPortalService.SendVerificationEmailAsync` previously called `_otpEmailSender.SendLoginOtpAsync(portalUser)` then generated an `EmailVerification` OTP; this redundant call was removed. The `OtpEmailSender.SendLoginOtpAsync` method remains for other flows (login of identity), not the portal.\n- **Email templates**: `Klinara.Web/Services/EmailTemplates.cs` was added with three constant-string templates (`OtpVerificationBody`, `AppointmentConfirmationBody`, `AppointmentReminderBody`) for OTP, confirmation, and reminder email bodies. These templates are defined as constants but not yet invoked in the service callbacks.\n- **DoctorSelector/SlotPicker integration**: `DoctorSelector` now injects `IScheduleService` and calls `GenerateSlotsForPeriodAsync(clinicId, doctorId, startDate, endDate)` when `LoadSchedule` is triggered. `SlotPicker` now injects `INavigationManager` and `IScheduleService`; `ConfirmSelection()` navigates to a confirmation page using `NavigationManager.NavigateTo()` with the slot and doctor IDs.\n\n## Project landmarks\n\n\nBackend portal work centers on `PatientTokenService`, `IPatientPortalService` / `PatientPortalService`, `PatientPortalController`, `ClinicSubdomainMiddleware`, `AppointmentService`, and `ErrorCodes`. Blazor portal components live under `Klinara.Web/Components/PatientPortal`; tests are in `Klinara.Tests`.
